# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Arcade Vault: a platform to play games online and compete for the highest score. The project follows a spec-driven workflow (`/spec` and `/spec-impl`) using the skills from https://github.com/Klerith/fernando-skills (installed via `npx skills@latest add Klerith/fernando-skills`). Spec 01 (`specs/01-mvp-pantallas-visuales.md`) built the visual MVP: five screens with mock data and a placeholder player. Spec 02 (`specs/02-home-page.md`) added the landing page at `/` and moved the library to `/biblioteca` (it supersedes the obsolete `specs/01-home-page.md`). Spec 03 (`specs/03-about-page-contacto.md`) added the About page at `/acerca` with a contact form that sends real email through Resend. Spec 04 (`specs/04-integracion-supabase.md`) laid the Supabase foundation (dependencies, env vars, browser and server clients) without touching any screen. Spec 05 (`specs/05-juego-rocas-asteroides.md`) made `rocas` (Asteroids) the first real game, playable at `/juegos/rocas/jugar` inside `GamePlayer`. Spec 06 (`specs/06-leaderboard-y-tabla-games.md`) created the `games` and `scores` tables in Supabase and made `/salon` and the top of `/juegos/[id]` read a real leaderboard. No auth exists yet.

No test runner is configured.

A project hook (`.claude/settings.json` → `.claude/hooks/lint-format.sh`, `PostToolUse` on `Write|Edit`) runs Prettier and then `eslint --fix` on every `.ts/.tsx/.js/.jsx/.mjs` file Claude writes, and Prettier on `.md` files. It skips `node_modules/`, `.next/` and `references/`; if ESLint leaves errors it exits with code 2 so they are fed back to Claude. Prettier uses its defaults (`.prettierrc.json`, `.prettierignore`).

## Architecture

- App Router only (`app/`); path alias `@/*` maps to the repo root.
- `next.config.ts` enables `cacheComponents`, `partialPrefetching` and `experimental.agentFeedback`. `cacheComponents` changes data-fetching/caching semantics, so check the docs before writing server components or fetches.
- Tailwind CSS v4 is wired through Turbopack: a `*.css` rule in `next.config.ts` uses the `@tailwindcss/turbopack` loader (no `tailwind.config`; theme tokens live in `@theme inline` in `app/globals.css`, with light/dark CSS variables via `prefers-color-scheme`).
- `app/layout.tsx` uses the globally typed `LayoutProps<"/">` helper (no import) and loads Press Start 2P / JetBrains Mono through `next/font/google` (`--font-press-start`, `--font-jetbrains`, exposed as `font-pixel` / `font-mono`). It mounts the background, `SessionProvider`, `Nav`, `<main>` and `Footer`.
- Routes: `/` (landing), `/biblioteca` (library), `/juegos/[id]` (detail), `/juegos/[id]/jugar` (player: real game for `rocas`, placeholder for the rest), `/acceso` (login), `/salon` (hall of fame), `/acerca` (about + contact form). Dynamic routes use `generateStaticParams` over `GAMES`; with `cacheComponents` an unknown `id` renders the 404 UI via `notFound()` but with HTTP 200 (`dynamicParams` is not supported).
- Mock data lives in `app/data/` (`types.ts`, `games.ts` with the catalog, `activity.ts` with the landing's recent scores and top players); the leaderboards are no longer mock (see Supabase below). `best` and `plays` in the catalog cards and detail page, and the landing's activity, are still mock. Shared client components are in `app/_components/`; the landing sections are Server Components in `app/_components/home/`, wrapped in the client `Reveal` (`app/_components/reveal.tsx`, reveal-on-scroll).
- Contact form: `app/acerca/page.tsx` is a Server Component; the only client piece is `app/_components/about/contact-form.tsx` (`useActionState` + client-side shake), which calls the Server Action `sendContact(prev, formData)` in `app/acerca/actions.ts`. The action runs a honeypot (`website`), server-side validation (name ≤ 80, email ≤ 254, message ≤ 2000, valid email format) and sends plain-text email with `resend` (`replyTo` = the user's email, subject `[Arcade Vault] Mensaje de <name>`). Missing config or provider errors are logged with `console.error` and the client only gets a generic message. Environment variables (in `.env.local`, git-ignored, server-only): `RESEND_API_KEY` (required), `CONTACT_TO_EMAIL` (required, recipient) and `CONTACT_FROM_EMAIL` (optional, defaults to `Arcade Vault <onboarding@resend.dev>`; in Resend test mode mail is only delivered to the account owner's address). Without `RESEND_API_KEY` the form shows its error state.
- Supabase (spec 04): project ref `ffpkjrmhlpjyljezclcf` (`https://ffpkjrmhlpjyljezclcf.supabase.co`, linked in `.mcp.json`); its database has the `games` and `scores` tables (spec 06, below). There is no `supabase/` folder: migrations are applied with the MCP `apply_migration` and documented in the specs. Dependencies: `@supabase/ssr` and `@supabase/supabase-js` (the latter only because `@supabase/ssr` needs it; never import `createClient` from it). Env vars, both public by design (they end up in the client bundle; data security will rely on RLS, not on hiding them): `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (the `sb_publishable_…` key, not the legacy `anon` one). They live in `.env.local` and in the versioned `.env.example` (`.gitignore` has the `!.env.example` exception). `SUPABASE_DB_PASSWORD` is a secret that stays only in `.env.local`; never commit it, `service_role` or any other secret.
- Supabase clients, both exported as `createClient`: `lib/supabase/client.ts` (`createBrowserClient`, for Client Components; the browser client is a singleton) and `lib/supabase/server.ts` (`createServerClient` + `cookies()` from `next/headers`; `async`, for Server Components, Server Actions and Route Handlers; create a new one per request, never a module-level instance). With `cacheComponents`, `cookies()` only works in a dynamic context (outside `"use cache"`, usually under `<Suspense>`). Only server code uses them today (`lib/leaderboard.ts` and the `submitScore` action) and there is no `proxy.ts`, so server-side session tokens are not refreshed until the Auth spec adds it. Both clients are typed with `Database` from `lib/supabase/database.types.ts`, generated with the MCP `generate_typescript_types` (regenerate it after any schema change; the view columns come out as `| null`). Realtime (`supabase.channel(...)`) and Edge Functions (`supabase.functions.invoke(...)`) will use these same clients; they need no extra setup and there is no `supabase/` folder or CLI config until a concrete function exists.
- Leaderboard (spec 06): tables `games` (`id`, `title`, `created_at`; one row, `rocas`; it defines which games have a ranking, the catalog still lives in `app/data/games.ts`) and `scores` (`id`, `game_id` FK to `games.id`, `player_name`, `score`, `created_at`; every saved match is kept; `check`s force `player_name = upper(btrim(...))` of 1–16 chars and `score` 0–9,999,999). Views: `game_leaderboard` (best score per player and game) and `global_leaderboard` (per player, the sum of best scores per game, with `updated_at` = latest `created_at`). Three migrations in the MCP history: `create_games_and_scores`, `disable_rls_games_and_scores` (the project has a `rls_auto_enable()` event trigger that turns RLS on for new tables), `global_leaderboard_add_updated_at`. **RLS is disabled on purpose for now (pending spec)**: anyone with the publishable key can read and write `scores`, and the views run with their creator's permissions (use `security_invoker = true` when RLS arrives). Anti-cheat, rate limiting and moderation of names do not exist; the player name is the identity (no `user_id` until Auth).
- Saving and reading scores: `lib/leaderboard.ts` (server only, dynamic via `cookies()`, so call it inside `<Suspense>`) exports `getBoards()` (GLOBAL + one board per row of `games`, top 10, ties broken by oldest `created_at`/`updated_at`) and `getGameBoard(id)` (`null` if the game is not in `games`). `submitScore(gameId, playerName, score)` in `app/juegos/[id]/jugar/actions.ts` validates (game exists, name 1–16 chars uppercased, integer score in range) and inserts with the server client; the client only gets generic errors, details go to `console.error`. `GamePlayer` calls it for games in `PLAYABLE_GAMES` (saving/error/retry states, link to `/salon`); placeholder games keep `saveScore` in `localStorage`. `usePlayerName()` (`app/_components/use-player-name.ts`) remembers the last successfully saved name in `av_player_name` and prefills the end-of-game modal (order: typed, remembered, session user, `INVITADO`). `/salon` (`app/salon/page.tsx`, Server Component) renders `HallOfFame` (client, tabs only) with `getBoards()` under `<Suspense>`; `/juegos/[id]` does the same with `Leaderboard` and `getGameBoard()` (`null` → "SIN PUNTUACIONES REALES TODAVÍA", empty list → "Sé el primero en entrar al salón de la fama"). To give a new game a ranking: insert a row in `games` and register its canvas in `PLAYABLE_GAMES`.
- Playable games (spec 05): `GamePlayer` (`app/_components/game-player.tsx`) is the frame and owns `paused` (only the PAUSA/REANUDAR button; no P/Esc, no auto-pause), `over` + the save-score modal and the React HUD (player, score, lives, level). `app/_components/games/registry.ts` exports `PLAYABLE_GAMES: Record<string, ComponentType<GameCanvasProps>>` mapping a catalog `id` to its canvas component; only `rocas` is registered, every other game keeps the placeholder with simulated score (`setInterval`, `POINTS_PER_LEVEL`). `GameCanvasProps` (`app/_components/games/types.ts`): `paused` (true while paused or with the end modal open), `onScore`, `onLives`, `onLevel` and `onGameOver(finalScore)` (called once when lives run out; the game draws no game-over screen). To add a game: build a canvas component with that contract and register it. `GamePlayer` passes `paused || over`, remounts the canvas with a `key` to restart (no `reset()`), and blurs the pause button after clicking so Space (fire) does not toggle it.
- Asteroids engine: `app/_components/games/asteroids/` has a React-free engine, `createAsteroidsGame(canvas, callbacks)` in `engine.ts` (returns `{ setPaused, destroy }`; callbacks fire only when the value changes), plus `entities.ts`, `input.ts`, `constants.ts`, `utils.ts` and the thin client component `asteroids-canvas.tsx` (creates the engine in `useEffect`, scales with `ResizeObserver` and `devicePixelRatio`). Logic runs in 800×600 logical coordinates and `draw()` applies `setTransform(canvas.width / W, …)` every frame, so the canvas pixel size can change freely. Colors come from the `--cyan`/`--magenta`/`--yellow`/`--green` tokens read with `getComputedStyle` at mount (hex fallbacks). The loop keeps drawing while paused (resizing clears a canvas) but stops updating. `input.ts` only calls `preventDefault` on arrows and Space while the game is active and focus is not in an `input`/`textarea`/`select`. Original game kept in `references/started-games/02-asteroids/` (never import from it). Keyboard only: no touch controls, sound or UFOs yet.
- Session and the scores of placeholder games are simulated in `localStorage` (`av_user`, `av_scores`) through `SessionProvider` / `useSession()` (`useSyncExternalStore`, so the first client render matches the server). It stays simulated and independent from Supabase until the Auth spec migrates it.
- Theme tokens (`--bg`, `--cyan`, …) are in `app/globals.css` and mapped in `@theme inline`. Effects Tailwind can't express (`av-bg`, `cover-*`, CRT, keyframes, `.btn`) are plain CSS there; `.btn` is in `@layer components` so utilities can override it. Caveat: `app/globals.css` also contains an unlayered copy of the template CSS (a second `.btn`, `.btn.xl`, `.btn.lg`, `.btn.magenta`, `av-bg`, keyframes…) that beats both the layered rules and Tailwind utilities. So `btn-xl`/`btn-lg`/`btn-magenta` have no effect; use the template modifiers (`btn xl`, `btn lg`, `btn magenta`) and the `!` important suffix (`hidden!`, `px-11!`) when overriding `.btn`.
- `references/templates/` is the original React-UMD prototype, kept only as a design reference (never import from it; `npm run lint` still reports errors there).
